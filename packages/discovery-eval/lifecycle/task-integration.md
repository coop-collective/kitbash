# Add shared review rooms to this existing application

Extend the supplied working Hono/Cloudflare application. Preserve its login, session revocation, profile concurrency, personal uploads, cached reports and existing browser flows. This is a local benchmark: keep its public demo credentials and existing dependency/runtime versions, do not deploy or contact external services. Alice and Bob already log in as `alice@example.test` / `bob@example.test`, with user IDs `user_alice` / `user_bob`.

Implement a coherent shared-team review feature, with automated tests, without replacing the host application:

* `POST /api/teams {name}` returns 201 `{id,name}`. Trim names, require 1–80 characters. The authenticated creator is the sole owner. `GET /api/teams` returns `{teams:[{id,name,role}]}` containing only the caller's teams. Persist teams and membership in D1 with new append-only migrations.
* `PUT /api/teams/:team/members/:userId {role:"member"}` adds either existing demo account or updates an existing non-owner member; return 204. `DELETE` at the same path removes a member, returning 204. Only the owner may manage membership; reject an unknown account with 400, attempts to change/remove the owner with 409, and non-owner management with 403. No invitation email flow is needed. Membership reads must consult current authority, not an authorization cache.
* Members can `POST /api/teams/:team/uploads` with raw bytes (at most 1 MiB), receiving 201 `{id}`, and `GET` or `DELETE /api/teams/:team/uploads/:id` (successful delete 204). Files belong to the team, so another current member can download/delete. Derive R2 keys from verified membership and a server-generated ID; an ID from another team must not expose or delete bytes. An unknown/foreign file returns 404 on GET; DELETE may return 404 or 204 while leaving bytes intact. Downloads must be byte-faithful attachments, `application/octet-stream`, `nosniff`, and `private, no-store`. Bound the actual incoming body, including chunked input. Reject over-limit bodies with 413. Persist metadata in D1. Existing personal uploads stay private to their original owner.
* `GET /api/teams/:team/rooms/:room/ws` upgrades an authenticated same-origin member to a WebSocket. Room names match `[A-Za-z0-9_-]{1,40}`; reject query strings and missing/foreign/`null` Origins. Never trust client-supplied identity headers: reject the request or strip/replace those headers with verified identity. An otherwise authorized member may connect after safe stripping. Unauthenticated team APIs return 401; a non-member gets 403 or 404. All HTTP mutations require same-origin Origin. Do not expose an unguarded DO forwarding or internal administration endpoint.
* Each team/room is independently coordinated by a SQLite Durable Object. Use the hibernation API (`acceptWebSocket`, serializable connection attachments, event methods); no socket map or recurring timer as authoritative state. Persist messages before broadcasting. A new connection gets `{type:"snapshot",messages:[{seq,userId,text}]}`, containing the latest 50 messages in ascending order. Client `{text}` produces `{type:"message",seq,userId,text}` to every connected member including the sender. Identity comes from the verified session. `seq` is a positive, strictly increasing integer per room, including after history pruning/restart. Distinct concurrent messages must each appear once. Room history survives a Wrangler process restart. Text must be nonblank and at most 1000 characters; JSON input must be text and at most 4096 UTF-8 bytes. Invalid/oversized input is rejected with an error event or socket close and must not enter history. Allow at least 60 valid messages at 100ms intervals in the acceptance run; do not rate-limit below that test workload.
* Phase-one socket authorization may use a bounded lease of at most five minutes, capped by the actual session expiry. HTTP requests and new handshakes initiated after a successful logout or membership-removal response completes must honor that change. Work already authorized before that response may finish. Application ping `ping` may auto-respond `pong` without waking state. Do not advertise exactly-once replay or platform billing guarantees.
* Add `/teams.html`, using the existing session/login. Provide `data-testid` controls: `team-name`, `team-create`, `team-select` (select of current teams), `room-name` (default `general`), `room-connect`, `room-status` (includes `connected` once usable), `message-text`, `message-send`, `room-messages`, `team-upload` (file input), `file-list` (download links after uploading). Creating a team adds/selects it. Connecting replaces rendered history with the snapshot; receiving messages renders text safely, not as HTML. File selection uploads automatically and creates a download link. Disable actions until ready, handle errors, and prevent duplicate live connections on reconnect. The existing homepage remains functional. Membership management may be API-only.

Keep existing migration files byte-for-byte and add new ones. Preserve existing test coverage; add meaningful tests for the new feature. Binding/class names and source organization are your choice. Generate binding types and run typecheck, tests, dry-run build and local migrations using the provided project tools. You may add ordinary package dependencies; do not change existing pinned toolchain versions or fetch other application source. Write a short `FEATURE-NOTES.md` explaining architecture, commands and remaining limitations. Requirements are fixed; an independent external checker will exercise APIs, browsers, hostile inputs, concurrent messages, persistent data and regressions.
