# Follow-up: read-only membership and retry-safe messages

Maintain the review-room feature already implemented in this application. All original requirements and existing app behavior continue to apply, including current data. Do not replace the application or reset D1/R2/DO storage. Preserve old SQL migration files and DO migration tags; use additive changes. Existing rooms contain history and files from before this change.

1. Extend the membership API to accept `role:"viewer"` alongside `member`. Viewers can list their teams, connect to rooms, receive history/live messages, and download team files. They cannot send messages, upload/delete files or manage membership. HTTP forbidden mutations return 403; forbidden socket sends return an error event or close without committing. Team listing returns the actual role. Keep the owner's role immutable.
2. Membership removal, downgrade and logout must take effect on already-open sockets. For application sends initiated after the successful HTTP mutation response completes, consult current authoritative session/membership permissions: authorize the sender before committing, and authorize each recipient before delivering that send. A removed/logged-out connection must neither commit a message nor receive its event; a downgraded viewer can continue to receive but cannot send. Work already authorized before that response may finish, and events already queued before it need not be retracted. Closing an idle connection immediately is optional. A five-minute lease alone is no longer sufficient. Internal fanout/control routes must remain inaccessible to public callers. Re-adding a member must allow a new connection without restoring a revoked login session.
3. Support an optional client-generated `clientId` matching `[A-Za-z0-9_-]{1,80}` in `{text,clientId}`. A successful new message with an ID includes `clientId` in its message event and in later snapshots. For the same authenticated user within the same team/room, an exact retry (including simultaneous retries on two sockets) returns `{type:"ack",seq,clientId}` only to the retrying socket, with the original sequence, and adds no message or duplicate broadcast. Check the sender's current session, membership and write permission before deduplication lookup, conflict handling or acknowledgment replay; a previous successful ID grants no authority to a removed, logged-out or read-only sender. Reusing the ID with different text yields `{type:"error",code:"conflict",clientId}` without changing history. Different users/rooms/teams may reuse an ID independently. Retain deduplication records even after the message leaves the latest-50 history window and across a process restart. Legacy messages and `{text}` clients still work; old history must remain readable. Validate provided IDs. Do not automatically resend a message from the UI after reconnect unless its identifier is preserved.
4. On `/teams.html`, a viewer's `message-send` and `team-upload` controls must be disabled after team selection/load; reading and connecting still work. Keep rendering safe, replacing history on reconnect, and show failures. The interface may require a refresh to display a newly changed role; server-side enforcement must be immediate at the boundary above.

Add regression tests for permissions and retry concurrency, rerun the fixed project checks, and update `FEATURE-NOTES.md`. Your implementation must preserve the prior phase's team membership, room history, team file bytes, personal profiles/files and sessions unless a test explicitly revokes one. An independent checker will verify before/after data, isolation, open connections, duplicate delivery and existing browser behavior.
